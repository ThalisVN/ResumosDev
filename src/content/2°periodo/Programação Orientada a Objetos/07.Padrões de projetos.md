## Padrões de Projeto
### 1. Introdução
O documento aborda a importância dos padrões de projeto (design patterns) no desenvolvimento de software orientado a objetos. Esses padrões são soluções reutilizáveis para problemas comuns, promovendo código elegante, flexível e de fácil manutenção. O conceito foi popularizado pelo livro "Design Patterns: Elements of Reusable Object-Oriented Software" (Gang of Four, 1994), que catalogou 23 padrões fundamentais.

### 2. Classificação dos Padrões de Projeto
Os padrões são divididos em três categorias principais:

#### 2.1 Padrões Criacionais
- **Objetivo**: Controlar a criação de objetos, evitando complexidade desnecessária.
- **Exemplos**:
  - **Singleton**: Garante uma única instância de uma classe (ex: gerenciador de arquivos).
  - **Factory Method**: Delega a criação de objetos para subclasses (ex: conexões com bancos de dados).
  - **Abstract Factory**: Cria famílias de objetos relacionados (ex: animais de estimação vs. selvagens).
  - **Builder**: Separa a construção de objetos complexos (ex: conversores de texto).
  - **Prototype**: Cria objetos clonando protótipos (ex: cópias de aplicativos estáveis).

#### 2.2 Padrões Estruturais
- **Objetivo**: Definir relacionamentos entre classes e objetos para formar estruturas flexíveis.
- **Exemplos**:
  - **Decorator**: Adiciona responsabilidades dinâmicas a objetos (ex: bordas em componentes GUI).
  - **Adapter**: Converte interfaces incompatíveis (ex: adaptadores para bancos de dados legados).
  - **Facade**: Simplifica interfaces complexas (ex: bibliotecas com métodos prontos para uso).
  - **Composite**: Representa hierarquias parte-todo (ex: estruturas de árvore).
  - **Proxy**: Controla acesso a objetos (ex: proxies para recursos remotos).

#### 2.3 Padrões Comportamentais
- **Objetivo**: Gerenciar comunicação e responsabilidades entre objetos.
- **Exemplos**:
  - **Observer**: Notifica objetos sobre mudanças de estado (ex: atualizações em interfaces gráficas).
  - **Strategy**: Encapsula algoritmos intercambiáveis (ex: estratégias de backup).
  - **Command**: Encapsula solicitações como objetos (ex: operações "desfazer" em editores).
  - **Template Method**: Define esqueletos de algoritmos (ex: cursos universitários com disciplinas variáveis).
  - **Chain of Responsibility**: Encadeia objetos para tratar solicitações (ex: handlers de erros em impressoras).

### 3. Padrões em Destaque

#### 3.1 Singleton
- **Propósito**: Garantir uma única instância de uma classe.
- **Implementação**:
  ```csharp
  public class Singleton {
      private static Singleton _instance;
      private Singleton() { }
      public static Singleton Instance {
          get {
              if (_instance == null) {
                  _instance = new Singleton();
              }
              return _instance;
          }
      }
  }
  ```
- **Vantagens**: Acesso global controlado, lazy initialization.
- **Desvantagens**: Dificuldade em testes unitários devido ao estado global.
## Banco de dados NoSQL

### 1. **Introdução ao NoSQL**
- **NoSQL (Not Only SQL)**: Classe de bancos de dados **não relacionais**.
- **Objetivo**: Oferecer alternativas para armazenamento e consulta de dados em cenários onde bancos relacionais são limitados (ex: alto volume, escalabilidade, flexibilidade).
- **Características Principais**:
  - Esquemas flexíveis ou inexistentes.
  - Dados semiestruturados ou não estruturados.
  - Alta escalabilidade horizontal.
  - Alta disponibilidade e desemviamento.
  - Consistência eventual (trade-off entre consistência e disponibilidade).
  - Modelos de replicação: mestre-escravo e mestre-mestre.
  - Particionamento horizontal (sharding).
### 2. **Origem e Evolução**
- Surgiu para atender demandas de **aplicações web em grande escala** (ex: Google, Facebook).
- Impulsionado pelo boom das pontocom (final dos anos 1990/início dos anos 2000).
- Popularizado por comunidades de código aberto (ex: MongoDB, Cassandra, Redis).
- Evoluiu para modelos de serviço gerenciado (DBaaS – Database as a Service).

### 3. **Categorias de Bancos NoSQL**

#### a. **Armazenamento Chave-Valor (Key-Value)**
- **Estrutura**: Pares chave-valor (ex: hashmap).
- **Exemplos**: Redis, DynamoDB, Azure Table Storage.
- **Uso ideal**:
  - Sessões de usuário.
  - Preferências e configurações.
  - Cache de alto desempenho.
  - Dados não estruturados.
- **Vantagens**: Simplicidade, escalabilidade, desempenho.

#### b. **Armazenamento Baseado em Documentos (Document Stores)**
- **Estrutura**: Dados armazenados como documentos (ex: JSON, XML).
- **Exemplos**: MongoDB, CouchDB.
- **Uso ideal**:
  - Catálogos de e-commerce.
  - Conteúdo dinâmico (blogs, plataformas de vídeo).
  - Dados semiestruturados com relacionamentos simples.
- **Vantagens**: Flexibilidade, consultas por campos, escalabilidade.

#### c. **Bancos de Dados de Grafos (Graph Databases)**
- **Estrutura**: Nós (entidades) e arestas (relacionamentos).
- **Exemplos**: Neo4j, Amazon Neptune.
- **Uso ideal**:
  - Redes sociais.
  - Detecção de fraudes.
  - Sistemas de recomendação.
  - Análise de conexões complexas.
- **Vantagens**: Consultas relacionais eficientes, suporte a ACID.

#### d. **Bancos Baseados em Colunas (Column-Family)**
- **Estrutura**: Dados armazenados por colunas ou famílias de colunas.
- **Exemplos**: Cassandra, HBase.
- **Uso ideal**:
  - Big Data.
  - Análise de dados em larga escala.
  - Logs e eventos.
- **Vantagens**: Desempenho em leituras massivas, escalabilidade.

### 4. **Características Comuns**
- **Escalabilidade Horizontal**: Adição de nós para expandir capacidade.
- **Disponibilidade**: Replicação de dados para tolerância a falhas.
- **Consistência Eventual**: Dados podem estar temporariamente inconsistentes.
- **Particionamento (Sharding)**: Divisão de dados para distribuir carga.
- **APIs Simples**: Operações básicas de CRUD via API.

### 5. **Comparação com Bancos Relacionais (SQL)**
| Aspecto               | SQL                          | NoSQL                       |
|-----------------------|------------------------------|-----------------------------|
| Esquema               | Fixo                         | Flexível                   |
| Escalabilidade        | Vertical                     | Horizontal                 |
| Consistência          | Forte (ACID)                 | Eventual (BASE)            |
| Modelo de Dados       | Tabelas                      | Documentos, Grafos, etc.   |
| Consultas             | SQL (poderoso)               | APIs simples               |
| Transações            | Suporte completo             | Limitado (exceto grafos)   |

### 6. **Conclusão**
- NoSQL é ideal para:
  - Aplicações modernas com alto volume de dados.
  - Cenários que exigem escalabilidade e flexibilidade.
  - Dados semiestruturados ou não estruturados.
- Cada categoria atende a necessidades específicas:
  - **Chave-valor**: Simplicidade e desempenho.
  - **Documentos**: Flexibilidade e consultas por campo.
  - **Grafos**: Relacionamentos complexos.
  - **Colunas**: Análise de grandes volumes.

#### 3.2 Decorator
- **Propósito**: Estender funcionalidades dinamicamente.
- **Exemplo Prático**:
  ```csharp
  public interface IComponent {
      string Operation();
  }
  public class ConcreteComponent : IComponent {
      public string Operation() => "Operação base";
  }
  public class DecoratorA : IComponent {
      private IComponent _component;
      public DecoratorA(IComponent component) => _component = component;
      public string Operation() => _component.Operation() + " + DecoratorA";
  }
  ```

#### 3.3 Observer
- **Propósito**: Notificar objetos dependentes sobre mudanças.
- **Componentes**:
  - **Subject**: Mantém uma lista de observers e notifica alterações.
  - **Observer**: Interface para objetos que recebem atualizações.
- **Exemplo em C#**:
  ```csharp
  public class Subject {
      public event Action<string> Notify;
      public void UpdateState(string state) => Notify?.Invoke(state);
  }
  ```

### 4. Arquitetura Multicamadas e MVC
- **Model-View-Controller (MVC)**:
  - **Model**: Gerencia dados e lógica de negócios.
  - **View**: Exibe dados (UI).
  - **Controller**: Intermediário entre Model e View.
- **Vantagens**: Separação de preocupações, reutilização de código.

### 5. Princípios SOLID
- **SRP (Single Responsibility)**: Uma classe deve ter uma única responsabilidade.
- **OCP (Open/Closed)**: Aberto para extensão, fechado para modificação.
- **LSP (Liskov Substitution)**: Subclasses devem substituir classes base sem quebrar o comportamento.
- **ISP (Interface Segregation)**: Interfaces específicas são melhores que interfaces genéricas.
- **DIP (Dependency Inversion)**: Depender de abstrações, não de implementações.

### 6. Conclusão
Os padrões de projeto e princípios SOLID são essenciais para:
- **Manutenibilidade**: Código mais fácil de modificar e estender.
- **Testabilidade**: Facilita a criação de testes unitários.
- **Reutilização**: Soluções comprovadas para problemas recorrentes.
- **Flexibilidade**: Adaptação a mudanças com menos impacto.
