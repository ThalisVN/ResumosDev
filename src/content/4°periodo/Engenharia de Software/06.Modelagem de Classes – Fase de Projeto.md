# Modelagem de Classes – Fase de Projeto

## 1. Introdução

- **Propósito central**: Traduzir os requisitos funcionais e não funcionais levantados nas etapas anteriores em uma estrutura técnica sólida, coesa e pronta para codificação.
    
- **Abordagem orientada a objetos**: Representa graficamente as entidades de domínio e de suporte técnico, definindo como atributos, métodos e relacionamentos operam em harmonia.
    
- **Transição da análise para o projeto**: Enquanto a análise foca no _o que_ o sistema deve fazer no domínio do negócio, a fase de projeto define _como_ a arquitetura de software implementará a solução técnica.
    

### Elementos Estruturais da Modelagem de Classes _(Bezerra, 2007)_

|**Elemento**|**Descrição**|
|---|---|
|**Classes**|Modelos abstratos ou planos de construção que representam conceitos, definindo atributos e comportamentos comuns para criação de instâncias.|
|**Atributos**|Características e dados armazenados pelos objetos que compõem uma classe.|
|**Métodos**|Operações, algoritmos e funções que expressam o comportamento da classe e regem sua comunicação.|
|**Relacionamentos**|Interações e conexões estruturais entre classes (associação, agregação, composição, herança e dependência).|

## 2. Aspectos da Modelagem na Fase de Projeto

A modelagem de classes estabelece o alicerce técnico que viabiliza o desenvolvimento sustentável _(Wazlawick, 2004; Sommerville, 2010)_.

- **Abstração e Modularidade**: Decompõe a complexidade do sistema em módulos independentes; alterações em uma classe não produzem impactos destrutivos em outros componentes.
    
- **Reutilização de Código**: Estruturação de hierarquias base para evitar redundâncias e acelerar a entrega de código limpo.
    
- **Comunicação Visual**: Facilita o alinhamento arquitetural entre analistas, arquitetos e engenheiros de software por meio da notação padronizada UML.
    
- **Base para Implementação**: Diagramas detalhados fornecem contratos claros (tipagem, visibilidade e parâmetros) para a codificação direta nas linguagens alvo.
    

## 3. Identificação e Definição Técnica

### Atributos e Tipagem _(Larman, 2008, 2011)_

- **Equilíbrio de granularidade**: Os atributos devem capturar apenas os dados necessários para as responsabilidades da classe, evitando modelos sobrecarregados ou restritivos demais.
    
- **Tipagem rigorosa**: Especificação explícita dos tipos de dados (tipos primitivos, coleções ou referências para outras classes do modelo).
    

### Métodos e Responsabilidades _(Pressman, 2011)_

- **Comportamentos coerentes**: Cada método deve atender diretamente ao propósito funcional da classe (ex.: `adicionarAoCarrinho()`, `atualizarPreco()`, `verificarDisponibilidade()`).
    
- **Assinaturas completas**: Definição de parâmetros de entrada, tipos de retorno e fluxo de tratamento de exceções.
    

## 4. Encapsulamento e Modificadores de Acesso

O encapsulamento oculta a lógica interna de processamento das classes e protege os dados contra manipulações indevidas, expondo apenas interfaces públicas seguras _(Larman, 2011; Pressman, 2011)_.

```
+ public        ➔  Acesso universal e irrestrito de qualquer ponto do código
# protected     ➔  Acesso restrito à própria classe e suas subclasses (hierarquia)
- private       ➔  Acesso estrito e exclusivo à classe onde foi declarado
```

|**Modificador**|**Símbolo UML**|**Escopo de Visibilidade**|**Exemplo Prático**|
|---|---|---|---|
|**Público (_public_)**|`+`|Acessível por qualquer classe ou componente do sistema.|Métodos de consulta ou ações externas (ex.: `+getNome()`).|
|**Privado (_private_)**|`-`|Acessível estritamente dentro da própria classe.|Atributos sensíveis e regras internas (ex.: `-saldo`).|
|**Protegido (_protected_)**|`#`|Acessível na própria classe e em suas classes derivadas/herdeiras.|Métodos compartilhados em hierarquia (ex.: `#emitirSom()`).|

## 5. Herança, Polimorfismo e Relacionamentos

A articulação entre os relacionamentos define a estrutura e a flexibilidade do design orientado a objetos _(Matos, 2003; Fowler, 2011)_.

- **Herança**: Mecanismo de especialização onde subclasses herdam características e comportamentos de uma superclasse base (ex.: `Carro` e `Moto` herdando da classe base `Veiculo`).
    
- **Polimorfismo**: Capacidade de manipular objetos de classes filhas distintas de forma uniforme a partir de uma interface comum (ex.: chamar `ligarMotor()` genericamente, permitindo que cada classe derivada execute sua versão do método).
    

### Comparativo de Relacionamentos Estruturais

|**Tipo**|**Notação / Semântica**|**Acoplamento / Ciclo de Vida**|
|---|---|---|
|**Associação**|Conexão semântica simples entre classes com multiplicidade definida.|`Cliente` associado a `Pedido`.|
|**Dependência**|Relação temporária onde uma classe depende de outra como parâmetro ou retorno.|`Pagamento` utilizando a classe `Banco` para transação.|
|**Agregação**|Vínculo "todo-parte" fraco; as partes sobrevivem sem o objeto todo.|`Biblioteca` agrega `Livros` (se a biblioteca fechar, os livros permanecem).|
|**Composição**|Vínculo "todo-parte" forte; as partes dependem existencialmente do todo.|`Carro` composto por `Rodas`.|

## 6. Padrões de Projeto (_Design Patterns_)

Soluções padronizadas, testadas e reutilizáveis para desafios recorrentes na arquitetura de software orientada a objetos _(Booch et al., 2006; Matos, 2003)_.

### Classificação dos Padrões

|**Categoria**|**Padrão**|**Propósito Principal**|**Exemplo Prático**|
|---|---|---|---|
|**Criacional**|**Factory Method** _(Pressman, 2011)_|Define uma interface para criar objetos, permitindo às subclasses decidirem qual classe concreta instanciar.|Instanciação desacoplada de diferentes tipos de produtos (`Roupas`, `Eletrônicos`).|
|**Criacional**|**Builder**|Separa a construção passo a passo de um objeto complexo de sua representação final.|Criação de personagens em jogos com diferentes combinações de equipamentos.|
|**Estrutural**|**Singleton**|Garante que uma classe possua apenas uma única instância ativa, fornecendo um ponto de acesso global.|Gerenciador centralizado de impressoras ou conexões de pool de recursos.|
|**Comportamental**|**Observer** _(Fowler, 2011)_|Estabelece uma dependência um-para-muitos; quando um objeto muda de estado, seus dependentes são notificados.|Notificação de estoque crítico para sistemas de vendas e logística.|
|**Comportamental**|**Strategy** _(Fowler, 2011)_|Define uma família de algoritmos intercambiáveis, encapsulando-os individualmente.|Implementação de diferentes formas de cálculo de taxas/frete em pagamentos.|

## 7. Ferramentas CASE para Modelagem de Projeto

As ferramentas CASE (_Computer-Aided Software Engineering_) suportam o refinamento visual dos diagramas de classes e de objetos, a consistência semântica e a automação _(Wazlawick, 2004; Sommerville, 2010)_.

- **Visual Paradigm**: Suporte a diagramas avançados, colaboração corporativa e sincronização com código-fonte.
    
- **Astah (antigo JUDE)**: Interface ágil com recursos visuais de arrastar e soltar e exportação de documentação técnica.
    
- **Geração e Engenharia Reversa**: Facilidade de transpor modelos conceituais para esqueletos de código e validar o design contra as regras de modelagem.
    

## 8. Conclusão

A modelagem de classes na fase de projeto estabelece a transição indispensável entre a análise e a codificação, fornecendo uma base técnica coesa, desacoplada e robusta. A combinação de encapsulamento com modificadores de acesso, herança, polimorfismo e a aplicação direcionada de padrões de projeto (_GoF_) garante que o software seja manutenível, escalável e fiel aos requisitos do negócio.
