# Gerenciamento de Transações
## 1. Introdução às Transações
- **Problema**: Operações de compra (ex: pagamento aprovado mas compra não confirmada) seriam catastróficas
- **Solução**: Transações garantem que todas as etapas ocorram com sucesso ou nenhuma seja aplicada
- **Definição**: Unidade de trabalho que consiste em uma ou mais operações no banco de dados

## 2. Propriedades ACID

| Propriedade | Descrição |
|-------------|-----------|
| **Atomicidade** | Todas as alterações são aplicadas ou nenhuma (tudo ou nada) |
| **Consistência** | Transação deixa o banco em estado consistente após conclusão |
| **Isolamento** | Transações não veem dados intermediários de outras transações simultâneas |
| **Durabilidade** | Alterações persistem mesmo em caso de falha do sistema |

## 3. Estados de uma Transação

```
Ativa → Parcialmente Confirmada → Confirmada
   ↓              ↓
 Falha ←──────────┘
   ↓
Abortada
```

| Estado | Significado |
|--------|-------------|
| **Ativa** | Estado inicial; transação em execução |
| **Parcialmente confirmada** | Última instrução executada; aguardando persistência |
| **Falha** | Execução normal não pode prosseguir |
| **Abortada** | Transação revertida (ROLLBACK); banco restaurado |
| **Confirmada** | Término bem-sucedido (COMMIT) |

## 4. Execuções Concorrentes

### Por que executar transações concorrentemente?
- Melhor uso do hardware (CPU processa enquanto disco lê/grava)
- Transações pequenas não ficam bloqueadas por transações longas

### Escalonador (Scheduler)
- Responsável por controlar a concorrência
- Evita interferências entre transações simultâneas

### Três Problemas da Concorrência

| Problema | Descrição | Exemplo |
|----------|-----------|---------|
| **Lost Update** (Atualização perdida) | Atualização de um usuário é sobrescrita por outro | Dois usuários alteram o mesmo saldo simultaneamente |
| **Dirty Read** (Leitura suja) | Transação lê valor atualizado por outra não confirmada | T2 lê valor que T1 ainda pode desfazer (ROLLBACK) |
| **Inconsistent Analysis** (Análise inconsistente) | Transação lê valores antes e depois de atualizações de outra | Agregação (SUM) calculada com dados mistos |

## 5. Mecanismos de Bloqueio (Locking)

### Modos de Bloqueio

| Tipo | Nome | Uso | Permite leitura? | Permite escrita? |
|------|------|-----|------------------|------------------|
| **Shared Lock (S)** | Bloqueio compartilhado (read lock) | Leitura de dados | ✅ Sim (múltiplos) | ❌ Não |
| **Exclusive Lock (X)** | Bloqueio exclusivo (write lock) | Leitura e escrita | ❌ Não | ❌ Não (apenas T1) |

### Matriz de Compatibilidade

| | Shared (S) | Exclusive (X) |
|--|------------|----------------|
| **Shared (S)** | ✅ Verdadeiro | ❌ Falso |
| **Exclusive (X)** | ❌ Falso | ❌ Falso |

### Regras
- **S + S** → permitido (múltiplas transações podem ler)
- **S + X** → não permitido (não pode escrever enquanto alguém lê)
- **X + X** → não permitido (apenas uma transação por vez)

## 6. Serialização de Transações

### Definição
- Uma programação (schedule) é **serializável** quando o resultado é igual ao obtido executando as transações em ordem serial (uma após a outra)

### Abordagens

| Abordagem | Descrição |
|-----------|-----------|
| **Conflict Serializability** | Verifica se há ciclos no grafo de precedência |
| **View Serializability** | Verifica equivalência de visualização |

### Grafo de Precedência
- Ciclo no grafo → programação **não** é serializável por conflito
- Sem ciclo → programação é **serializável**

## 7. Implementação de Transações em SQL

### Comandos Básicos

| Comando | Funcionalidade |
|---------|----------------|
| `START TRANSACTION` | Inicia uma nova transação |
| `COMMIT` | Confirma a transação; torna mudanças permanentes |
| `ROLLBACK` | Desfaz a transação; cancela mudanças |

### AUTOCOMMIT
- **Comportamento padrão** do MySQL e SQL Server: cada comando SQL é uma transação individual confirmada automaticamente
- **Desabilitar**: `SET autocommit = 0;`

### Exemplo 1 – Desfazendo (ROLLBACK)
```sql
SET autocommit = 0;
START TRANSACTION;
INSERT INTO departments ...;  -- comando 1
INSERT INTO employees ...;     -- comando 2
INSERT INTO dept_manager ...;  -- comando 3 (falha por CONSTRAINT)
ROLLBACK;  -- desfaz comandos 1 e 2
```

### Exemplo 2 – Confirmando (COMMIT)
```sql
START TRANSACTION;
INSERT INTO departments ...;
INSERT INTO employees ...;
INSERT INTO dept_manager ...;  -- com sucesso
COMMIT;  -- confirma todas as alterações
```

### Isolamento na Prática
- Duas transações simultâneas (T1 altera, T2 consulta)
- T2 não vê a alteração até T1 executar COMMIT
- Resultado: T2 vê valor antigo (consistência)

### ⚠️ Comandos Irreversíveis
- **DDL** (CREATE, ALTER, DROP) não podem ser revertidos com ROLLBACK
- Planeje transações sem incluir tais declarações

## 8. Conclusão

### Resumo dos Conceitos

| Conceito | Descrição |
|----------|-----------|
| **Transação** | Unidade de trabalho com uma ou mais operações |
| **ACID** | Atomicidade, Consistência, Isolamento, Durabilidade |
| **Estados** | Ativa → Parcialmente confirmada → Confirmada / Falha → Abortada |
| **Concorrência** | Execução simultânea para melhor uso do hardware |
| **Lost Update** | Atualização sobrescrita por outra transação |
| **Dirty Read** | Leitura de dado ainda não confirmado |
| **Locking** | Mecanismo para evitar conflitos (Shared X Exclusive) |
| **Serialização** | Garantia de consistência em execuções concorrentes |
| **COMMIT / ROLLBACK** | Confirmação ou reversão da transação |

### Pontos-Chave para o Desenvolvedor
1. Use **START TRANSACTION** para agrupar comandos que devem ser atômicos
2. Em caso de erro, execute **ROLLBACK** para desfazer todas as alterações
3. Execute **COMMIT** apenas quando todas as operações forem bem-sucedidas
4. Lembre-se: **DDL** (CREATE, ALTER, DROP) são irreversíveis
5. O SGBD gerencia **isolamento** automaticamente – transações não veem dados não confirmados de outras
