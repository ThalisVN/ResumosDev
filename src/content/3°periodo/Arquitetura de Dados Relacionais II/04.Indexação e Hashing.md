# Indexação e Hashing
## 1. Introdução à Indexação
- **Problema**: Grandes massas de dados tornam a busca lenta sem orientação
- **Analogia**: Índice de livro ou bibliotecário – localiza informações rapidamente
- **Função do índice**: Encontrar registros de forma mais rápida no banco de dados

## 2. Conceitos e Importância dos Índices

### Estrutura B-Tree (Árvore B)
- Estrutura mais utilizada por SGBDs para índices
- Organização hierárquica: **nível raiz** → **nós galhos** → **nível folha**

### Processo de busca na B-Tree (ex: encontrar cliente 14)
1. Nó raiz: valores > 10 estão à direita
2. Nó intermediário: valor < 15
3. Nó intermediário: valor > 12
4. Nível folha: registro encontrado (clientes 13 e 14)

### Índice por Hash
- Distribuição uniforme por buckets (baldes)
- Função de hash define o bucket (ex: `n % 13`)
- Aplicação: databases in-memory, columnstore databases

### Candidatos a Indexação
| Critério | Exemplo |
|----------|---------|
| Campos únicos e chaves primárias | `PRIMARY KEY` |
| Colunas em predicados de igualdade | `WHERE codcliente = 10` |
| Colunas em ORDER BY, GROUP BY, JOINs | `ORDER BY nome` |
| Colunas com LIKE (depende) | `WHERE nome LIKE 'João%'` |

### Custo dos Índices
- Toda manipulação (INSERT, UPDATE, DELETE) exige atualização do índice
- **Trade-off**: consultas mais rápidas × operações de escrita mais lentas

## 3. Índices Agrupados (Clustered) vs Não Agrupados (Nonclustered)

| Tipo | Característica | Quantidade por tabela |
|------|----------------|----------------------|
| **Agrupado (Clustered)** | Define a ordem sequencial do armazenamento dos dados | **1** (um) |
| **Não agrupado (Nonclustered)** | Ordem diferente da sequência do arquivo | **Vários** |

### Implementação por SGBD

| SGBD | Comportamento |
|------|---------------|
| **MySQL (InnoDB)** | PRIMARY KEY = índice clustered. Se não houver PK, usa primeiro UNIQUE NOT NULL |
| **SQL Server** | Permite especificar `CLUSTERED` ou `NONCLUSTERED` no CREATE INDEX |
| **Oracle** | Similar ao MySQL |

## 4. Boas Práticas de Indexação

### ✅ Recomendações

| Prática | Motivo |
|---------|--------|
| Criar índice agrupado (PK ou UNIQUE) | Define ordenação física dos dados |
| Indexar colunas usadas em WHERE, JOIN, ORDER BY, GROUP BY | Otimiza consultas frequentes |
| Avaliar cardinalidade | Índices com baixa cardinalidade são mais eficientes |

### ❌ O que evitar
- **Não indexar colunas com muitas atualizações** (INSERT, UPDATE, DELETE frequentes)
- **Não criar índices desnecessários** – cada índice custa em operações de escrita

## 5. Construção e Gerenciamento de Índices com SQL

### Comandos DDL

| Comando | Funcionalidade |
|---------|----------------|
| `CREATE INDEX nome ON tabela (coluna)` | Criar índice não agrupado |
| `CREATE CLUSTERED INDEX ...` (SQL Server) | Criar índice agrupado |
| `CREATE NONCLUSTERED INDEX ...` (SQL Server) | Criar índice não agrupado |
| `ALTER TABLE ADD CONSTRAINT PRIMARY KEY ...` | Criar índice clustered (MySQL) |

### Consulta de Metadados (INFORMATION_SCHEMA.STATISTICS)
```sql
SELECT table_schema, table_name, index_name, 
       column_name, cardinality, index_type
FROM INFORMATION_SCHEMA.STATISTICS
WHERE table_schema = 'employees';
```

### Cardinalidade
- **Definição**: Grau de exclusividade dos valores em uma coluna indexada
- **Uso**: Otimizador do SGBD usa a cardinalidade para decidir qual índice utilizar
- **Regra**: Índices com **baixa cardinalidade** são preferidos (menos registros para ler)

## 6. Otimização de Consultas com Índices

### Sem Índice (Full Table Scan)
- O SGBD lê **toda a tabela** (ex: 2.844.047 registros para encontrar 63)
- Performance degradada em tabelas grandes

### Com Índice
- Leitura apenas dos registros relevantes (ex: 63 registros)
- Operação: `non-unique key lookup`

### Quando o Índice NÃO é Usado
- Otimizador pode optar por `full table scan` se:
  - Consulta mal escrita
  - Função na coluna indexada (ex: `YEAR(data) = 2024`)
  - Volume de leitura estimado é muito alto

### Exemplo de consulta que inviabiliza índice
```sql
-- EVITA usar índice em to_date
WHERE YEAR(de.to_date) = '9999'

-- USARIA índice em to_date
WHERE de.to_date BETWEEN '9999-01-01' AND '9999-12-31'
```

## 7. Verificação de Tabelas sem Índice Primário
```sql
SELECT t.table_schema, t.table_name, s.index_name
FROM INFORMATION_SCHEMA.TABLES t
LEFT JOIN INFORMATION_SCHEMA.STATISTICS s 
    ON s.table_name = t.table_name AND s.INDEX_NAME = 'PRIMARY'
WHERE t.table_schema = 'employees' AND t.table_type = 'BASE TABLE'
ORDER BY s.cardinality ASC;
```

## 8. Conclusão

### Resumo dos Conceitos

| Conceito | Descrição |
|----------|-----------|
| **Índice** | Estrutura para acesso rápido aos dados |
| **B-Tree** | Estrutura hierárquica mais comum para índices |
| **Clustered** | Define ordem física da tabela (1 por tabela) |
| **Nonclustered** | Índice separado da tabela (vários permitidos) |
| **Cardinalidade** | Grau de exclusividade – usada pelo otimizador |
| **Full Table Scan** | Leitura completa da tabela (sem índice ou índice ignorado) |

### Pontos-Chave para o Administrador de Dados
- **Criar índices** para consultas frequentes (WHERE, JOIN, ORDER BY, GROUP BY)
- **Evitar índices** em colunas com muitas operações de escrita
- **Monitorar cardinalidade** para avaliar eficiência dos índices
- **Garantir** que pelo menos um índice clustered exista por tabela
- **Escrever consultas** que permitam o uso correto dos índices (evitar funções em colunas indexadas)
