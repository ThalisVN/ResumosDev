# Controle de Concorrência
## 1. Introdução ao Controle de Concorrência
- **Contexto**: Múltiplas transações executando simultaneamente no banco de dados
- **Objetivo**: Garantir que transações ocorram de forma segura, atendendo às regras ACID
- **Problemas a evitar**:
  - Perda da consistência do banco de dados
  - Acesso a dados inconsistentes
  - Perda de atualizações de dados

## 2. Conceito de Bloqueio (Lock)

**Definição**: Quando uma transação precisa de garantia de que um objeto não mudará enquanto estiver ativa, ela adquire um bloqueio sobre esse objeto, impedindo que outras transações o alterem.

### Modos de Bloqueio Básicos

| Tipo | Nome | Uso | Característica |
|------|------|-----|----------------|
| **Compartilhado (S)** | Shared Lock / Read Lock | Leitura | Permite múltiplas leituras simultâneas |
| **Exclusivo (X)** | Exclusive Lock / Write Lock | Leitura e escrita | Apenas uma transação por vez |

## 3. Protocolos para Tratamento de Concorrência

### 3.1 Protocolo com Base em Bloqueios

#### Tipos de Bloqueio

| Tipo | Descrição |
|------|-----------|
| **Bloqueio binário** | Dois estados: bloqueado (lock) ou desbloqueado (unlock). Aplicável a nível de linha, tabela ou banco inteiro |
| **Bloqueio compartilhado/exclusivo** | Diferencia bloqueios por tipo de operação (leitura vs escrita) |

#### Two-Phase Locking (2PL) – Protocolo de Duas Fases

| Fase | Característica |
|------|----------------|
| **Fase de crescimento** | Transação pode obter bloqueios, mas não pode liberar nenhum |
| **Fase de encolhimento** | Transação pode liberar bloqueios, mas não pode obter novos |

**Objetivo**: Assegurar a serialização das transações

### 3.2 Protocolo com Base em Timestamp

**Timestamp**: Identificador único criado pelo SGBD (contador lógico ou data/hora)

#### Metadados por Item de Dados (Q)

| Campo | Significado |
|-------|-------------|
| **W-timestamp(Q)** | Maior timestamp de qualquer transação que gravou (write) com sucesso em Q |
| **R-timestamp(Q)** | Maior timestamp de qualquer transação que leu (read) com sucesso em Q |

#### Regras do Protocolo

**Operação READ(Q) pela transação Ti:**
- Se `TS(Ti) < W-timestamp(Q)` → leitura **rejeitada**; Ti é revertida
- Se `TS(Ti) > W-timestamp(Q)` → leitura **executada**; R-timestamp(Q) = TS(Ti)

**Operação WRITE(Q) pela transação Ti:**
- Se `TS(Ti) < R-timestamp(Q)` → escrita **rejeitada**; Ti é revertida
- Se `TS(Ti) < W-timestamp(Q)` → escrita **rejeitada**; Ti é revertida
- Senão → escrita **executada**; W-timestamp(Q) = TS(Ti)

#### Vantagens do Protocolo por Timestamp
- ✅ Garante serialização por conflito
- ✅ **Garante liberdade de impasse** (nenhuma transação espera)

## 4. Deadlock (Impasses)

### Definição
Ocorre quando duas ou mais transações estão simultaneamente aguardando, cada uma esperando a liberação de um bloqueio para prosseguir.

### Exemplo de Deadlock
- Transação 52 aguarda liberação de lock exclusivo da Transação 62
- Transação 62 requisita acesso de leitura a dados modificados pela Transação 52
- Resultado: impasse (deadlock)

### Tratamento por SGBD

| SGBD | Estratégia |
|------|-------------|
| **SQL Server** | Detecta a cada 5 segundos; escolhe vítima (menor custo ou menor prioridade); aborta e reverte |
| **MySQL (InnoDB)** | Prefere eliminar transações longas em vez de analisar deadlocks |
| **Outros** | Usam mecanismo de timeout (tempo de espera) |

### Grafo de Espera
- Ferramenta visual para detectar deadlocks
- Disponível em SGBDs como SQL Server

## 5. Níveis de Isolamento (ANSI SQL 92)

### Comando para definir nível de isolamento
```sql
SET TRANSACTION ISOLATION LEVEL [nível];
```

### Tabela de Níveis de Isolamento

| Nível | Características | Problemas que Permite | SGBD Padrão |
|-------|----------------|----------------------|-------------|
| **READ UNCOMMITTED** | SELECT sem bloqueio; pode ler versão anterior da linha | Leitura suja (dirty read) | – |
| **READ COMMITTED** | Não lê dados modificados não confirmados | Leituras não repetíveis (valores podem mudar na mesma transação) | SQL Server, Oracle |
| **REPEATABLE READ** | Leitura consistente baseada no snapshot da primeira leitura | Fantasmas (phantom reads) | MySQL |
| **SERIALIZABLE** | Nenhuma transação modifica dados lidos por outra até conclusão | Nenhum (mais restritivo) | – |

### Resumo dos Problemas Evitados por Nível

| Nível de Isolamento | Dirty Read | Non-Repeatable Read | Phantom Read |
|---------------------|------------|---------------------|--------------|
| READ UNCOMMITTED | ✅ Permite | ✅ Permite | ✅ Permite |
| READ COMMITTED | ❌ Evita | ✅ Permite | ✅ Permite |
| REPEATABLE READ | ❌ Evita | ❌ Evita | ✅ Permite |
| SERIALIZABLE | ❌ Evita | ❌ Evita | ❌ Evita |

### ⚠️ Aviso sobre SERIALIZABLE
Pode causar problemas de performance significativos. Usar com cautela.

## 6. Conclusão

### Resumo dos Conceitos

| Conceito | Descrição |
|----------|-----------|
| **Controle de concorrência** | Mecanismos para garantir execução segura de transações simultâneas |
| **Lock (bloqueio)** | Impede que outras transações atuem sobre um objeto |
| **Two-Phase Locking (2PL)** | Protocolo que assegura serialização (crescimento → encolhimento) |
| **Timestamp** | Identificador único usado em protocolo livre de deadlock |
| **Deadlock** | Impasse onde transações esperam umas pelas outras |
| **Níveis de isolamento** | Controlam o grau de interferência entre transações concorrentes |

### Pontos-Chave
1. **Bloqueios não são problemas** – são mecanismos para garantir ACID
2. **Two-Phase Locking** garante serialização (crescimento → encolhimento)
3. **Protocolo por timestamp** evita deadlocks completamente
4. **Deadlocks** ocorrem mesmo com protocolos; SGBDs têm mecanismos para detectar e resolver
5. **Níveis de isolamento** permitem balancear desempenho × consistência
6. Escolha o nível de isolamento adequado à necessidade da transação (ex: relatórios podem tolerar leitura suja; transações financeiras exigem SERIALIZABLE)
